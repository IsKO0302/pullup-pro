# Архитектура PULLUP PRO 2.0

PULLUP PRO 2.0 — local-first приложение для тренировок. Один и тот же веб-клиент работает как сайт, как устанавливаемое PWA и как Telegram Mini App. Сервер (API + PostgreSQL) и Telegram-бот нужны только для входа, синхронизации между устройствами, облачных фото и напоминаний. Без сервера приложение полностью работает на устройстве.

```
 ┌──────────── устройство пользователя ────────────┐
 │  apps/web  (браузер · PWA · Telegram Mini App)  │
 │  localStorage pullup.pro.v2 + IndexedDB          │
 │  service worker: офлайн-оболочка приложения     │
 └───────────────┬──────────────────────────────────┘
                 │ HTTPS  /api/*  (Bearer-токен)
 ┌───────────────▼──────────────┐     ┌──────────────────────────┐
 │ apps/api  (Fastify 5)        │     │ apps/telegram-bot (grammY)│
 │ вход Telegram, синхронизация,│     │ команды, вход по ссылке,  │
 │ фото, экспорт, удаление,     │     │ напоминания (раз в минуту)│
 │ раздача apps/web/dist        │     └──────┬─────────────┬─────┘
 └───────────────┬──────────────┘            │             │ Bot API
                 │            ┌──────────────┘             ▼
         ┌───────▼────────────▼──┐                 api.telegram.org
         │ PostgreSQL 14+        │
         └───────────────────────┘
```

## Клиент (apps/web)

- **Маршруты** (hash-роутер `core/router.ts`): `home`, `train`, `plan`, `programs`, `calendar`, `journal`, `stats`, `report`, `body`, `nutrition`, `mu`, `achievements`, `library`, `group`, `builder`, `profile`, `settings`. Hash-маршрутизация не требует настройки сервера и одинаково работает в PWA и Mini App.
- **Состояние**: один объект `AppState` (`packages/shared/src/types.ts`), версия `STATE_VERSION = 2`. Хранится в `localStorage` под ключом `pullup.pro.v2` и зеркалируется в IndexedDB (`kv`). Активная тренировка — отдельный ключ `pullup.pro.run`, поэтому перезагрузка или закрытие вкладки не теряют её. Фото прогресса — бинарно в IndexedDB (`photos`).
- **Данные 1.0** (`pullup.pro.v1`) только читаются для однократной миграции и никогда не изменяются и не удаляются.
- **Снимки безопасности** (`services/snapshots.ts`): перед демо-данными, импортом, сбросом и восстановлением текущее состояние копируется в IndexedDB (запасной вариант — `pullup.pro.snap.<вид>`), откат доступен в настройках.
- **Движок тренировок** (`packages/shared/src/engine.ts`): подбирает упражнения под оборудование и уровень, хранит дозу каждого упражнения, предлагает прогрессию только с подтверждением пользователя, снижает нагрузку при боли, предлагает лёгкую тренировку после очень тяжёлой и разгрузочную неделю после 6 недель регулярных тренировок.
- **Статистика** считается чистыми функциями только из реальных записей; при нехватке данных выводится честное «нет данных».

## Синхронизация (local-first)

1. Состояние раскладывается на записи `{c, id, u, del, d}` (`toRecords`): коллекции-одиночки `profile`, `settings`, `mu`, `nutrition`, `engine`; списки `sessions`, `tests`, `custom`, `body`, `bodyFields`, `photos`, `foods`, `products`, `reminders`; словари `plan`, `ach`, `daily`, `progress`.
2. Клиент хранит индекс хешей (`pullup.pro.sync`). После каждого сохранения `diffState` помечает изменённые записи, `u` — время изменения на устройстве.
3. `POST /api/sync/push` (до 500 записей за запрос, каждая проверяется zod и лимитом 256 КБ): сервер принимает запись, если её `u` новее сохранённой (last-writer-wins), и присваивает ей ревизию пользователя `rev`. Более старая версия возвращается клиенту как конфликт вместе с серверной копией. Повторная отправка той же версии идемпотентна.
4. `GET /api/sync/pull?since=<rev>` отдаёт записи новее известной ревизии, включая «надгробия» удалённых записей.
5. Синхронизация запускается после входа, после изменений (с задержкой), при возвращении сети и вручную. Офлайн-изменения копятся и отправляются при восстановлении связи (проверено в e2e).

Ограничение LWW: при одновременном редактировании одной и той же записи на двух устройствах побеждает более позднее время устройства; на корректность влияет точность часов устройств.

## Вход и безопасность

- **Telegram Mini App**: клиент отправляет `Telegram.WebApp.initData` в `POST /api/auth/telegram`. Сервер проверяет подпись HMAC-SHA-256 (ключ — `HMAC_SHA256("WebAppData", BOT_TOKEN)`), сравнение в постоянном времени, свежесть `auth_date` (`INITDATA_MAX_AGE`, по умолчанию 24 ч). Подделанные, изменённые и просроченные данные отклоняются с кодами `initdata_bad_hash` / `initdata_expired`.
- **Браузер / PWA**: `POST /api/auth/link/start` выдаёт одноразовый код (10 минут) и секрет; пользователь открывает `t.me/<bot>?start=link_<code>`, бот спрашивает «Включить синхронизацию?», после подтверждения клиент получает токен через `POST /api/auth/link/poll` по секрету.
- **Сессии**: случайный токен 32 байта, в базе хранится только SHA-256, срок `SESSION_TTL_DAYS` (90 дней). Выход удаляет сессию.
- **Фото** уходят на сервер только после отдельного явного согласия; тип файла проверяется по сигнатуре (JPEG/PNG/WebP), лимит `MAX_PHOTO_MB`, квота 1 ГБ на пользователя; отзыв согласия удаляет все фото с сервера.
- **Приватность**: `GET /api/export` — выгрузка всех данных, `DELETE /api/account` — удаление аккаунта со всеми записями и фото. Бот не показывает личные данные в групповых чатах.
- **Заголовки**: CSP (`script-src 'self' https://telegram.org`, `frame-ancestors` для Telegram Web), `nosniff`, `referrer-policy`, `permissions-policy`, HSTS при HTTPS; `/api/*` — `no-store`; `index.html`, `sw.js`, `version.json`, `manifest.webmanifest` не кэшируются браузером.
- **Rate limit**: `RATE_LIMIT` запросов в минуту на IP, отдельно `AUTH_RATE_LIMIT` для входа. За прокси нужен `TRUST_PROXY=true`.
- Все пользовательские запросы ограничены `user_id` текущей сессии; изоляция пользователей проверяется интеграционными тестами.

## Telegram-бот

- Режим **polling** (по умолчанию, не нужен публичный адрес) или **webhook** (`WEBHOOK_URL` на HTTPS + `WEBHOOK_SECRET`, проверка заголовка `X-Telegram-Bot-Api-Secret-Token`).
- При старте (`BOT_SETUP_PROFILE=true`) задаёт команды RU/EN, описания и кнопку меню «PULLUP PRO» (только для HTTPS `WEBAPP_URL`).
- Данные для ответов берёт из той же базы (синхронизированные записи); без синхронизации объясняет, как её включить, и не придумывает цифры.
- **Напоминания** (тренировка, вес, вода, мобилити) настраиваются в приложении и синхронизируются. Цикл раз в минуту проверяет локальное время пользователя (часовой пояс профиля, иначе `DEFAULT_TZ`) в окне `REMINDER_WINDOW_MIN`. Отправка резервируется в `reminder_log` (одно напоминание в локальный день, атомарно через `INSERT … ON CONFLICT DO NOTHING`), напоминание о тренировке пропускается, если тренировка уже была. Ответ 403 (бот заблокирован) ставит напоминания на паузу.

Подробнее: [TELEGRAM_SETUP.md](TELEGRAM_SETUP.md).

## PWA

Service worker генерируется при сборке (`apps/web/vite.config.ts`): список предварительного кэширования — все файлы сборки, версия — хеш содержимого. Кэшируется только оболочка приложения; `/api/*` и пользовательские данные — никогда. Новая версия ждёт подтверждения пользователя и не прерывает тренировку. Подробнее: [PWA_SETUP.md](PWA_SETUP.md).

## Сборка и запуск

- Клиент: `vite build` → `apps/web/dist` (+ `sw.js`, `version.json`).
- API и бот: `scripts/bundle.mjs` (esbuild) собирает каждый сервис в один ESM-файл; пакеты `@pullup/*` встраиваются, npm-зависимости ставятся `npm ci --omit=dev`.
- API раздаёт `apps/web/dist` (или каталог из `WEB_DIST`) с fallback на `index.html`, применяет миграции и зеркалирует каталог при старте.

Развёртывание: [DEPLOYMENT.md](DEPLOYMENT.md).
