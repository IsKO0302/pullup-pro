# Безопасность PULLUP PRO

Документ описывает **фактически реализованные** меры (код указан) и честно перечисляет то, что не закрыто. Проверка — автотесты из [TESTING.md](TESTING.md).

## 1. Модель угроз

| Актив | Где живёт | Кто может прочитать |
|---|---|---|
| Тренировки, замеры, питание, профиль | `localStorage` + зеркало IndexedDB на устройстве; по желанию — таблица `records` на сервере | только владелец устройства; на сервере — только владелец аккаунта |
| Фото прогресса | на устройстве (по умолчанию); в облаке (`photos`) — только после отдельного согласия | только владелец |
| Токен бота | переменная окружения сервера | никто, кроме процессов API и бота |
| Токены сессий | клиент (Bearer) + SHA-256 в БД | владелец сессии |

Принцип: **local-first**. Без входа и синхронизации данные никогда не покидают устройство.

## 2. Вход через Telegram (Mini App)

Реализация: `apps/api/src/telegram-auth.ts`, маршрут `POST /api/auth/telegram` (`apps/api/src/app.ts`).

1. Клиент отправляет **оригинальную строку `Telegram.WebApp.initData`**. `initDataUnsafe` для проверки личности не используется.
2. Сервер считает `secret_key = HMAC_SHA256("WebAppData", BOT_TOKEN)`, строит `data_check_string` (все поля кроме `hash`, по алфавиту, `key=value` через `\n`) и сравнивает `HMAC_SHA256(secret_key, data_check_string)` с `hash` через `timingSafeEqual`. Это алгоритм из <https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app>.
3. Проверяется `auth_date`: старше `INITDATA_MAX_AGE` (по умолчанию 24 ч) → `expired`; из будущего (> 5 мин) → `future`.
4. Идентификатор пользователя берётся **только** из подписанного поля `user`. Идентификатор из тела запроса или заголовков не принимается как доказательство личности.
5. После проверки сервер выдаёт собственную сессию: случайный токен 256 бит (`randomBytes(32)`), в БД хранится только его SHA-256 (`auth_sessions.token_hash`), срок — `SESSION_TTL_DAYS` (90 по умолчанию). Просроченные сессии удаляются housekeeping-функцией (`packages/db/src/repos.ts`).
6. Лимит запросов на вход: `AUTH_RATE_LIMIT` в минуту с IP. Токен бота не попадает в клиентский код (проверка — раздел 8).

Вход в браузере/PWA — одноразовый код через бота (`/api/auth/link/*`): код живёт 10 минут, секрет опроса хранится как SHA-256 и сравнивается за постоянное время, код одноразовый.

## 3. Авторизация и разделение данных

- Каждый защищённый маршрут проходит `requireUser` (Bearer-токен → пользователь). Без валидной сессии — `401`.
- Все запросы к данным в `packages/db/src/repos.ts` ограничены `WHERE user_id = $1`; идентификатор берётся из сессии, а не из запроса. Чужой `id` фото или записи даёт `404`/пустой результат.
- Таблицы связаны `ON DELETE CASCADE` с `users`: удаление аккаунта (`DELETE /api/account`) стирает записи, фото, сессии и журнал напоминаний.
- Тесты `tests/integration/api.test.ts`: «users never see each other's data», «another user cannot read the photo», «account deletion removes all personal data», «logout invalidates the token».

## 4. Защита API

| Мера | Реализация |
|---|---|
| Валидация входа | zod-схемы для каждого маршрута и каждой коллекции синхронизации (`packages/shared/src/schema.ts`), ограничение размера записи (`MAX_RECORD_BYTES`), отклонение U+0000, проверка `id` |
| Лимит запросов | `@fastify/rate-limit`: `RATE_LIMIT` (300/мин) глобально, `AUTH_RATE_LIMIT` (30/мин) на вход |
| Размер тела | 1 МБ по умолчанию, 16 МБ для синхронизации, `MAX_PHOTO_MB` для фото |
| Prototype pollution | `onProtoPoisoning/onConstructorPoisoning: 'error'`; миграция данных игнорирует опасные ключи |
| Фото | реальный тип определяется по сигнатуре (JPEG/PNG/WebP), заявленный `content-type` не доверяется; квота 1 ГБ на пользователя |
| Ошибки | единый формат; для 5xx наружу уходит общий текст, детали — в лог; заголовок `Authorization` вырезается из логов |
| CORS | выключен по умолчанию (одна origin); при необходимости — только список из `CORS_ORIGINS` |
| Заголовки | `Content-Security-Policy` (скрипты только `self` и `telegram.org`, `frame-ancestors` — только Telegram), `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` (камера/микрофон/гео запрещены), HSTS на HTTPS |
| Кеш | ответы `/api/*` — `Cache-Control: no-store`; Service Worker не кеширует `/api/*` |

### Telegram-бот

- Личные данные показываются **только в личном чате** и только для аккаунта Telegram, которому они принадлежат (`guard` в `apps/telegram-bot/src/bot.ts`); в группах — отказ.
- Напоминания — только по явному включению пользователем, с учётом его часового пояса; блокировка бота останавливает рассылку.
- Webhook-режим требует `WEBHOOK_SECRET` (16–256 символов).

## 5. Данные на устройстве

- Перед импортом, сбросом, демо-режимом и восстановлением создаётся снимок-копия (`apps/web/src/services/snapshots.ts`).
- Service Worker удаляет только свои старые кеши (`pullup-pro-*`) и не трогает `localStorage`/IndexedDB: данные **не удаляются при обновлении** (тест `pwa.spec.ts`).
- Данные 1.0 только читаются при миграции, ключ `pullup.pro.v1` не изменяется.

## 6. Конфиденциальность фото и здоровья

- Фото по умолчанию не покидают устройство. Облачное хранение — отдельное согласие (`POST /api/account/consent`); отзыв согласия удаляет все фото с сервера.
- Приложение не определяет процент жира или медицинское состояние по фото и не заявляет этого.
- Все расчёты питания — приблизительные и помечены как такие; приложение не заменяет врача.

## 7. Что нужно сделать владельцу при развёртывании

1. Хранить `.env` вне Git (`.gitignore` исключает `.env`, `.env.*`, кроме `.env.example`). Токен бота не отправлять в чат и не коммитить.
2. Если токен мог попасть в чужие руки — `/revoke` в @BotFather, затем обновить `BOT_TOKEN`.
3. Включить HTTPS (Caddy-профиль в `docker-compose.yml`), задать `TRUST_PROXY=true` за прокси, чтобы лимиты считались по реальному IP.
4. Использовать длинный пароль PostgreSQL, не публиковать порт БД наружу.
5. Делать резервные копии БД (см. [DEPLOYMENT.md](DEPLOYMENT.md)).

## 8. Проверка отсутствия секретов в клиенте

```bash
# в сборке веб-приложения не должно быть токена бота и имён серверных переменных
grep -rEn "BOT_TOKEN|[0-9]{8,}:[A-Za-z0-9_-]{30,}" apps/web/dist || echo "чисто"
```

## 9. Известные ограничения

- Конфликты синхронизации разрешаются по принципу «последняя запись побеждает» по времени устройств; при сильно расходящихся часах побеждает запись с «более поздними» часами.
- Облачные фото хранятся в PostgreSQL **без шифрования на уровне приложения** (защита — доступ к БД и шифрование диска хостингом). Для production с чувствительными фото стоит добавить шифрование на стороне клиента.
- Проверка с настоящим Telegram (реальный токен, клиент на телефоне) не выполнялась — требуется внешний доступ; логика подписи покрыта тестами с вручную подписанными данными.
